1. WHAT IS THIS PROJECT?
================================================================================

SMEIC stands for "School Canteen Management System." It is a website that
helps schools manage their canteen (cafeteria/food court). Think of it like
a mini-Amazon, but specifically for school food.

It has FOUR types of users:

  ADMIN          → The school staff who manages everything
  STUDENT        → The students who order food
  PARENT         → The parents who put money in their child's wallet
  CANTEEN STAFF  → The people who cook and serve the food

Each type of user sees a DIFFERENT dashboard when they log in. This is called
"Role-Based Access Control" — meaning what you can see and do depends on your
role (admin, student, parent, or canteen staff).

WHY WAS THIS BUILT?
  → To replace paper-based canteen systems
  → To let parents track what their children eat
  → To let students order food without standing in line
  → To help canteen staff manage orders efficiently
  → To give admins a bird's-eye view of everything

2. HOW DOES THE BACKEND WORK? (THE BIG PICTURE)
================================================================================

Imagine the backend like a restaurant:

  1. A CUSTOMER (your browser) places an ORDER (sends a request)
  2. The WAITER (public/index.php) takes the order
  3. The waiter sends it to the right CHEF (Controller) based on what you ordered
  4. The CHEF prepares the dish (talks to the database)
  5. The dish is served back to you (HTML page or JSON response)

In technical terms:

  BROWSER → sends HTTP request → public/index.php (front controller)
  → reads the "action" parameter → calls the right Controller method
  → Controller talks to MySQL database using PDO
  → Controller renders a PHP view file (the HTML page you see)
  → Response is sent back to your browser

The KEY concept is: EVERYTHING goes through ONE file — public/index.php.
This file is called the "Front Controller." It's like the main reception
desk of a hotel — every request passes through it.

Here is a simplified version of what happens (in code):

  // This is in public/index.php
  $action = $_GET['action'] ?? 'home';   // What page did the user want?

  switch ($action) {
      case 'login':
          (new AuthController())->login();      // Show login page
          break;
      case 'student/dashboard':
          (new StudentController())->dashboard(); // Show student dashboard
          break;
      case 'student/cart':
          (new StudentController())->cart();      // Show student cart
          break;
      // ... hundreds more routes
  }

So when you visit:
  http://localhost/SMEIC/public/index.php?action=student/cart

The system reads "student/cart" and calls the StudentController's cart() method.
That method fetches the cart items from the database and renders the cart page.

WHAT IS A CONTROLLER?
  A Controller is a PHP file that contains the business logic. Think of it as
  the "brain" for a specific section. For example:
    - AuthController handles login, logout, password changes
    - StudentController handles everything students do
    - AdminController handles everything admins do
    - CanteenController handles everything canteen staff do
    - ParentController handles everything parents do

WHAT IS A VIEW?
  A View is a PHP file that contains HTML (the visual part of the page).
  Views are like templates — they display data that the Controller gives them.
  For example, views/student/dashboard.php shows the student dashboard.

3. WHAT TECHNOLOGIES ARE USED?
================================================================================

Let's break down every technology and WHY it's used:

PHP 8.0+
  WHAT: A server-side programming language. This is the MAIN language of the backend.
  WHY:  It's simple, widely supported, and runs on almost any hosting server.
  NOTE: We use plain PHP — no framework like Laravel. This keeps it simple.

MySQL 5.7+ (or MariaDB 10.3+)
  WHAT: A database system. It stores all the data — users, orders, menu items, etc.
  WHY:  It's reliable, fast, and free. Works perfectly with PHP.
  NOTE: The database is called "smeic_canteen" and has 19 tables.

PDO (PHP Data Objects)
  WHAT: A PHP feature that lets you talk to databases safely.
  WHY:  It uses "prepared statements" which PREVENT hackers from injecting
        malicious SQL code (this is called SQL Injection prevention).
  HOW:  Every single database query in this project uses PDO. We NEVER
        concatenate (join) user input into SQL strings. This is the most
        important security practice in the entire codebase.

Apache 2.4 (via XAMPP)
  WHAT: The web server that receives HTTP requests and sends responses.
  WHY:  XAMPP bundles Apache + MySQL + PHP together, making local development easy.
  HOW:  The .htaccess files tell Apache which files to allow/block.

TailwindCSS (via CDN)
  WHAT: A CSS framework that makes styling web pages fast and easy.
  WHY:  Instead of writing thousands of lines of CSS from scratch, we use
        Tailwind's pre-built classes like "bg-blue-500" or "rounded-lg".
  CDN:  We load it from a CDN (content delivery network) so no installation needed.

Vanilla JavaScript (no React/Vue/jQuery)
  WHAT: Plain JavaScript without any framework.
  WHY:  Keeps things simple. We use it for AJAX calls, sidebar toggling,
        and notification polling.

Chart.js 4.4
  WHAT: A JavaScript library for creating charts and graphs.
  WHY:  Used on dashboards to show things like "orders per week" or
        "monthly revenue" as nice visual charts.

Composer
  WHAT: A tool for installing PHP libraries (like npm for JavaScript).
  WHY:  We use it for optional features like PDF generation and QR codes.
  NOTE: The app works WITHOUT Composer — it just falls back to simpler alternatives.

chillerlan/php-qrcode (optional)
  WHAT: A library that generates QR codes in PHP.
  WHY:  Used to generate QR codes for order pickup tokens offline.

dompdf (optional)
  WHAT: A library that converts HTML to PDF.
  WHY:  Used for generating PDF reports in the admin panel.

phpmailer (optional)
  WHAT: A library for sending emails from PHP.
  WHY:  Used for password reset emails. Currently writes to a log file instead.

5. HOW REQUESTS FLOW THROUGH THE SYSTEM
================================================================================

Let's trace what happens when a student adds an item to their cart:

STEP 1: Student clicks "Add to Cart" button on the menu page
  → JavaScript function smeicAjax() is called

STEP 2: JavaScript sends an AJAX POST request to:
  → public/api/update-cart.php

STEP 3: update-cart.php includes _bootstrap.php (sets up session, headers)
  → Checks: Is the user logged in? Is this a student?
  → Checks: Does the CSRF token match?
  → Reads the item ID and quantity from the request

STEP 4: Database operation:
  → $pdo->prepare("INSERT INTO carts (student_id, menu_item_id, quantity) 
                    VALUES (?, ?, ?) ON DUPLICATE KEY UPDATE quantity = ?")
  → This is a PREPARED STATEMENT — the ? marks are filled in safely
  → No user input is ever directly put into SQL queries

STEP 5: Response:
  → Returns JSON: { "ok": true, "quantity": 2, "cart_count": 3 }
  → The JavaScript updates the cart badge number in the sidebar

STEP 6: Student sees:
  → The cart badge now shows "3" (total items in cart)
  → A toast notification appears: "Added to cart!"

THIS IS THE COMPLETE FLOW FOR EVERY ACTION IN THE APP:
  Browser → Front Controller → Controller Method → Database → Response → Browser

6. HOW LOGIN AND AUTHENTICATION WORKS
================================================================================

When someone tries to log in, here's exactly what happens:

STEP 1: User enters their login info and clicks "Login"
  → The form sends a POST request to: index.php?action=login

STEP 2: AuthController::login() runs:
  → Reads the "role" (admin/student/parent/canteen) and "identifier" (email/ID)
  → Looks up the user in the CORRECT table based on role:
      admin   → users table WHERE email = ?
      student → students table WHERE student_id = ?
      parent  → parents table WHERE parent_id = ? OR email = ?
      canteen → users table WHERE email = ? AND role = 'canteen'

STEP 3: Password check:
  → password_verify($_POST['password'], $row['password'])
  → This compares the entered password against the stored bcrypt hash
  → bcrypt is a ONE-WAY hash — you can't reverse it to get the password
  → Example: "Admin@123" might be stored as "$2y$10$xK9..."
  → password_verify() knows how to check if "Admin@123" matches that hash

STEP 4: On successful login:
  → session_regenerate_id(true)  ← Creates a NEW session ID
      WHY?  Prevents "session fixation" attacks where an attacker
            sets your session ID before you log in
  → Stores user info in $_SESSION:
      $_SESSION['user_id']    = the user's ID
      $_SESSION['role']       = 'student' / 'admin' / 'parent' / 'canteen'
      $_SESSION['name']       = the user's name
      $_SESSION['force_change'] = 1 if they need to change password

STEP 5: Redirect:
  → If force_change = 1 → redirect to change-password page
  → Otherwise → redirect to their dashboard

WHAT IF THE PASSWORD IS WRONG?
  → Shows "Invalid login credentials" error
  → Does NOT tell the attacker WHICH part was wrong (email or password)
  → This is a security best practice

WHAT ABOUT FORCE PASSWORD CHANGE?
  → All demo accounts have force_password_change = 1
  → After first login, the user MUST change their password
  → Until they do, they CANNOT access any other page
  → This is enforced by this code in public/index.php:

  if (!empty($_SESSION['user_id']) && (int)$_SESSION['force_change'] === 1) {
      if (!in_array($action, ['change-password', 'logout', 'login'], true)) {
          redirect(url('index.php?action=change-password'));
      }
  }

7. HOW SESSIONS WORK
================================================================================

A "session" is like a temporary memory that the server keeps for each logged-in
user. It's how the server remembers who you are as you move from page to page.

HOW IT WORKS:
  1. When you log in, the server creates a SESSION FILE on the server
  2. It sends your browser a COOKIE (a small piece of data) with a session ID
  3. Every time you visit a new page, your browser sends that cookie back
  4. The server reads the session ID, finds your session file, and knows it's YOU

SESSION SETTINGS (in config/functions.php):
  session_name('SMEIC_SESSID');        // Custom name (not the default PHPSESSID)
  session lifetime = 4 hours           // Auto-logout after 4 hours
  httponly = true                      // JavaScript can't read the cookie
  samesite = 'Lax'                    // Prevents CSRF attacks

  WHY httponly?  If a hacker injects malicious JavaScript (XSS attack), they
                 can't steal your session cookie because JavaScript can't see it.

  WHY SameSite=Lax?  When you click a link from another website, your session
                      cookie is NOT sent. This prevents CSRF attacks.

SESSION KEYS STORED:
  user_id      → Your unique ID
  role         → 'admin', 'student', 'parent', or 'canteen'
  name         → Your display name
  username     → Your username (for canteen staff)
  force_change → 1 if you must change password, 0 if not
  csrf_token   → Your security token for this session
  flash        → Temporary success/error messages

HELPER FUNCTIONS:
  current_user()     → Returns all your session info, or null if not logged in
  require_login()    → Redirects to login page if not logged in
  require_role()     → Redirects if you don't have the right role

8. HOW CSRF PROTECTION WORKS
================================================================================

CSRF stands for "Cross-Site Request Forgery." It's an attack where a hacker
tricks you into performing an action you didn't intend to.

EXAMPLE OF A CSRF ATTACK:
  1. You are logged into SMEIC
  2. You visit a malicious website
  3. That website has a hidden form that automatically submits a request to
     transfer money from your wallet to the hacker's account
  4. Your browser sends the request WITH your session cookie
  5. SMEIC thinks YOU made the request — and transfers the money!

HOW WE PREVENT IT:

  STEP 1: When you log in, the server generates a random TOKEN:
    $_SESSION['csrf_token'] = bin2hex(random_bytes(32));
    // Example: "a3f8b2c1d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9..."

  STEP 2: Every form on the site includes this token as a hidden field:
    <input type="hidden" name="csrf_token" value="a3f8b2c1d4e5f6...">

  STEP 3: When you submit the form, the server checks:
    if (hash_equals($_SESSION['csrf_token'], $_POST['csrf_token'])) {
        // Token matches — this is a legitimate request
    } else {
        // Token doesn't match — REJECT the request
    }

  WHY hash_equals()?  It's a "constant-time" comparison function. Regular
  string comparison (==) can leak information about the token through
  timing differences. hash_equals() always takes the same amount of time
  regardless of where the strings differ.

  FOR AJAX CALLS:  JavaScript sends the token in a header:
    X-CSRF-Token: a3f8b2c1d4e5f6...

9. HOW PASSWORDS ARE STORED
================================================================================

NEVER store passwords as plain text. If someone hacks your database, they'd
see every user's password. Instead, we use HASHING.

WHAT IS HASHING?
  Hashing is a ONE-WAY transformation. You can turn a password INTO a hash,
  but you CANNOT turn a hash BACK into a password.

  Plain text:  "Admin@123"
  Bcrypt hash: "$2y$10$xK9Z8Q7W6E5R4T3Y2U1I0O9P8L7K6J5H4G3F2D1S0A9Z8X7C6V5"

  When someone logs in with "Admin@123", PHP calculates the hash and
  compares it to the stored hash. If they match, the password is correct.

THE CODE:
  // To store a password:
  $hash = password_hash('Admin@123', PASSWORD_BCRYPT);
  // Cost factor: 10 (default, good balance of speed and security)

  // To verify a password:
  password_verify('Admin@123', $stored_hash);  // Returns true or false

WHERE PASSWORDS ARE STORED:
  The same password is stored in TWO places (kept in sync):
    1. students.password    (for students)
    2. parents.password     (for parents)
    3. canteen_staff.password (for canteen staff)
    4. users.password       (mirror for admin, parent, canteen)

  WHY TWO PLACES?  Because the login system checks the "users" table first,
  then looks up extra details in the role-specific table. Both need the
  password hash for verification to work.

WHAT IS BCRYPT?
  Bcrypt is a specific hashing algorithm designed for passwords.
  - It's SLOW (by design) — makes brute-force attacks impractical
  - It includes a SALT (random data) — prevents rainbow table attacks
  - The cost factor (10) means it does 2^10 = 1024 rounds of hashing
  - Each hash is UNIQUE even for the same password

10. HOW THE DATABASE WORKS
================================================================================

The database is called "smeic_canteen" and contains 19 tables. Think of each
table like an Excel spreadsheet with rows and columns.

ALL 19 TABLES EXPLAINED:

1. users
   Stores login accounts for admin, parent, and canteen staff.
   Columns: id, role (admin/parent/canteen), email, password, force_password_change, is_active
   WHY:  A central place to check login credentials for these three roles.

2. students
   Stores student profiles.
   Columns: id, student_id (S10001), full_name, class_name, roll_no, behavioral_score, parent_id, password
   WHY:  Each student has their own account linked to a parent.

3. parents
   Stores parent profiles.
   Columns: id, parent_id (P10001), full_name, email, phone, address, wallet_balance, password
   WHY:  Parents manage their child's wallet and track spending.

4. canteen_staff
   Stores canteen staff accounts.
   Columns: id, full_name, email, username, password, role (manager/staff), permissions
   WHY:  Different staff members can have different permissions.

5. wallets
   Stores student wallet balances.
   Columns: student_id (unique), balance
   WHY:  Each student has exactly one wallet with a balance.

6. transactions
   Records every money movement (credit or debit).
   Columns: user_id, user_type, amount, type (credit/debit), reference, balance_after

DATABASE CONNECTION CODE:
  The database connection is in config/database.php. Here's what it does:

  $pdo = new PDO(
      "mysql:host=127.0.0.1;dbname=smeic_canteen;charset=utf8mb4",
      "root",
      ""
  );

  - host: 127.0.0.1 = the database is on the same computer
  - dbname: smeic_canteen = the name of our database
  - charset: utf8mb4 = supports all characters including emojis
  - root = the default MySQL username on XAMPP
  - "" = the default MySQL password on XAMPP (empty)

PREPARED STATEMENTS:
  Instead of writing:
    ❌ "SELECT * FROM students WHERE student_id = '$user_input'"
    (This is DANGEROUS — a hacker could type: ' OR '1'='1 and get all students)

  We write:
    ✅ $stmt = $pdo->prepare("SELECT * FROM students WHERE student_id = ?");
    $stmt->execute([$user_input]);
    (The ? is a PLACEHOLDER — PHP safely inserts the value separately)

  This is the SINGLE MOST IMPORTANT security practice in the entire codebase.

AUTO-MIGRATIONS:
  When the app starts, smeic_run_schema_migrations() checks if all columns
  and tables exist. If any are missing (e.g., after an upgrade), it adds them
  automatically. This means upgrades are seamless.

11. HOW MONEY (WALLET) OPERATIONS WORK
================================================================================

This is the MOST CRITICAL part of the system. Money bugs can cause real harm.

THERE ARE THREE TYPES OF MONEY OPERATIONS:

1. ADMIN TOP-UP:  Admin adds money to a parent or student wallet
2. PARENT TRANSFER: Parent sends money from their wallet to their child's wallet
3. STUDENT CHECKOUT: Student pays for food from their wallet

ALL THREE USE THE SAME SAFETY PATTERN:

  Step 1: START A TRANSACTION
    $pdo->beginTransaction();
    // This means: "I'm about to do multiple database changes.
    //              If anything goes wrong, undo EVERYTHING."

  Step 2: LOCK THE WALLET ROW
    $stmt = $pdo->prepare("SELECT balance FROM wallets WHERE student_id=? FOR UPDATE");
    $stmt->execute([$student_id]);
    $balance = (float)$stmt->fetchColumn();

    // FOR UPDATE means: "Lock this row so no one else can change it
    //                    while I'm working. This prevents two people
    //                    from spending the same money at the same time."

  Step 3: CHECK IF ENOUGH MONEY
    if ($balance < $total) {
        throw new RuntimeException('Insufficient balance');
    }

  Step 4: DEDUCT THE MONEY
    $pdo->prepare("UPDATE wallets SET balance = balance - ? WHERE student_id = ?")
        ->execute([$total, $student_id]);

  Step 5: CREATE THE ORDER AND TRANSACTION RECORD
    // Insert into orders table
    // Insert into order_items table
    // Insert into transactions table (debit record)
    // Send notifications

  Step 6: COMMIT (save everything)
    $pdo->commit();
    // All changes are saved permanently.

  IF ANYTHING GOES WRONG:
    $pdo->rollBack();
    // Everything is UNDONE — as if nothing happened.
    // The student keeps their money. No partial orders.

WHY TWO TRANSACTION RECORDS FOR TRANSFERS?
  When a parent transfers ₹100 to a child:
    - Parent gets a DEBIT transaction: -₹100
    - Child gets a CREDIT transaction: +₹100
  This ensures the "books always balance" — like a real bank.

CHECKOUT SPECIFICALLY:
  When a student checks out:
    1. Lock the student's wallet row (FOR UPDATE)
    2. Check if balance >= order total
    3. Deduct the total from wallet
    4. Create the order (status: pending)
    5. Create order_items (snapshot of items and prices)
    6. Create transaction record (debit)
    7. Clear the student's cart
    8. Notify canteen staff (new order!)
    9. Notify the parent (your child ordered food)
    10. Commit everything

  If ANY step fails, everything is rolled back. No partial orders, no lost money.

12. HOW ORDERS WORK (ORDER LIFECYCLE)
================================================================================

Every order goes through these stages:

  PENDING → ACCEPTED → PREPARING → READY → PICKED_UP
     │         │           │          │
     └─────────┴───────────┴──────────┘
                    ↓
              CANCELLED (at any stage before pickup)

DETAILED EXPLANATION:

1. PENDING
   - Student places the order
   - Money is deducted from wallet
   - Canteen staff sees a new order
   - Parent gets a notification

2. ACCEPTED
   - Canteen staff clicks "Accept"
   - They can set an estimated prep time (e.g., "10 minutes")
   - Student gets notified: "Your order has been accepted!"

3. PREPARING
   - Food is being cooked/prepared
   - (Optional intermediate stage)

4. READY
   - Canteen staff clicks "Mark Ready"
   - ready_at timestamp is set (records the exact time)
   - Student gets notified: "Your order is ready for pickup!"
   - Parent gets notified too
   - 3-MINUTE REMINDER TIMER STARTS:
     - Every 60 seconds, the system checks: "Has it been 3+ minutes?"
     - If yes: sends a "Please pick up your order!" reminder
     - Maximum 3 reminders
     - This prevents food from sitting uncollected

5. PICKED_UP
   - Student shows their QR code at the canteen
   - Staff scans/enters the 6-digit token
   - System marks the order as picked up
   - Student gets notified: "Order complete! Enjoy your meal!"

6. CANCELLED
   - Canteen staff can cancel at any stage BEFORE pickup
   - FULL REFUND is automatically issued to student's wallet
   - Student and parent are notified

PICKUP TOKENS:
  - 6-digit random number (e.g., 847291)
  - Generated using random_int() (cryptographically secure)
  - Contains NO personal information (just a random number)
  - Expires after 24 hours
  - Rate limited: max 5 verification attempts per 15 minutes
  - Every verification attempt is logged for security

13. HOW NOTIFICATIONS WORK
================================================================================

Notifications are in-app messages that alert users about important events.

WHEN NOTIFICATIONS ARE SENT:
  - Student places an order → canteen + parent get notified
  - Canteen accepts order → student gets notified
  - Canteen marks order ready → student + parent get notified
  - Canteen cancels order → student + parent get notified
  - Admin tops up wallet → recipient gets notified
  - Parent transfers money → child gets notified
  - 3-minute pickup reminder → student gets notified

HOW THE NOTIFICATION BELL WORKS:
  1. The sidebar has a bell icon with a badge showing unread count
  2. Every 10 seconds, JavaScript calls: api/check-notifications.php
  3. The API returns: { "count": 3, "latest": { "title": "Order Ready!", ... } }
  4. If count > 0, the bell badge shows the number
  5. A toast notification pops up with the latest message

THE CODE (in notifications.js):
  setInterval(function() {
      smeicAjax('api/check-notifications.php', {}, function(data) {
          if (data.count > 0) {
              bellBadge.textContent = data.count;
              showToast(data.latest.title, data.latest.message);
          }
      });
  }, 10000);  // Every 10,000 milliseconds = 10 seconds

PICKUP REMINDERS (in api/check-pickup-reminders.php):
  - Runs every 60 seconds (triggered by notifications.js)
  - Finds orders where: status='ready' AND ready_at < NOW - 3 minutes
  - Sends a reminder notification to the student
  - Maximum 3 reminders per order
  - Idempotent: safe to call multiple times (won't send duplicate reminders)

14. HOW FILE UPLOADS WORK
================================================================================

Canteen staff can upload images for menu items. Here's how it works:

VALIDATION CHECKS (in CanteenController::menuSave()):
  1. FILE SIZE: Must be under 4MB
  2. MIME TYPE: Must be an image (jpg, png, webp) — checked with mime_content_type()
  3. DIMENSIONS: getimagesize() verifies it's actually an image file
  4. FILENAME: Renamed with uniqid() — NEVER use the user's original filename

  WHY RENAME?  If a user uploads a file called "hack.php.jpg", we don't want
  to save it with that name. By renaming it to something like "6654a3b2c1.jpg",
  we eliminate any risk of the file being executed as code.

STORAGE:
  Images are saved to: public/assets/uploads/menu/
  The database stores just the filename (not the full path).

DISPLAY:
  The menu_image() helper function returns the image URL:
    - If the file exists: returns the path to the uploaded image
    - If not: returns a placeholder image

15. HOW QR CODES AND PICKUP TOKENS WORK
================================================================================

When a student places an order, a 6-digit pickup token is generated:

TOKEN GENERATION (in generate_pickup_token()):
  $token = str_pad(random_int(100000, 999999), 6, '0', STR_PAD_LEFT);

  - random_int() is CRYPTOGRAPHICALLY SECURE (not rand() or mt_rand())
  - The token is a 6-digit number: 100000 to 999999
  - This gives 900,000 possible combinations — hard to guess

TOKEN VERIFICATION:
  When the student arrives at the canteen:
  1. They show their QR code (or tell the staff the 6-digit number)
  2. Staff enters the token at: canteen/scan-pickup
  3. System checks:
     - Does the token match an order?
     - Is the order in "ready" status?
     - Is the token expired (24-hour limit)?
     - Has the student exceeded the rate limit (5 attempts per 15 min)?
  4. If all checks pass: order is marked as "picked_up"

QR CODE GENERATION:
  Two methods:
  1. OFFLINE (preferred): chillerlan/php-qrcode library
     - Generates QR code directly in PHP
     - Works without internet
  2. ONLINE (fallback): api.qrserver.com
     - If the library isn't installed
     - Requires internet connection

RATE LIMITING:
  - Maximum 5 token verification attempts per session
  - If exceeded: 15-minute lockout
  - Prevents brute-force attacks on the 6-digit token
  - Every attempt is logged in token_verification_log table

17. HOW SECURITY IS HANDLED
================================================================================

Here is a COMPLETE list of every security measure in the project:

1. SQL INJECTION PREVENTION
   Every database query uses PDO prepared statements.
   User input is NEVER concatenated into SQL strings.
   This is verified across the ENTIRE codebase — zero exceptions.

2. CROSS-SITE SCRIPTING (XSS) PREVENTION
   All output is escaped via e() = htmlspecialchars($val, ENT_QUOTES, 'UTF-8').
   This converts special characters to safe HTML entities:
     < becomes &lt;
     > becomes &gt;
     " becomes &quot;
     ' becomes &#039;
   Example: If someone puts <script>alert('hacked')</script> as their name,
            it displays as plain text, not executable code.

3. CROSS-SITE REQUEST FORGERY (CSRF) PREVENTION
   Every form includes a hidden csrf_token field.
   Every AJAX call includes an X-CSRF-Token header.
   Tokens are validated with hash_equals() (constant-time comparison).
   Tokens are generated once per session using bin2hex(random_bytes(32)).

4. SESSION FIXATION PREVENTION
   session_regenerate_id(true) is called on every successful login.
   This creates a new session ID, making the old one useless to attackers.

5. PASSWORD SECURITY
   Stored as bcrypt hashes (PASSWORD_BCRYPT, cost 10).
   Never stored as plain text.
   Never logged or displayed anywhere.

6. SECURITY HEADERS (set in views/layouts/header.php)
   X-Content-Type-Options: nosniff       → Prevents MIME type sniffing
   X-Frame-Options: SAMEORIGIN           → Prevents clickjacking
   X-XSS-Protection: 1; mode=block       → Browser XSS filter
   Referrer-Policy: strict-origin...     → Controls referrer info
   Permissions-Policy: camera=()         → Disables camera/mic/geo
   Strict-Transport-Security: max-age... → Forces HTTPS
   Content-Security-Policy               → Controls allowed resources

7. FILE UPLOAD SECURITY
   MIME type validation (mime_content_type)
   Image dimension validation (getimagesize)
   Maximum file size (4MB)
   Filenames renamed (uniqid) — user input never trusted

8. WALLET INTEGRITY
   SELECT ... FOR UPDATE row-level locks
   PDO transactions with commit/rollback
   Atomic operations — all or nothing

9. ACCESS CONTROL
   require_role(['admin']) at top of every controller method
   Force password change on first login

10. DIRECTORY PROTECTION
    Root .htaccess blocks access to config/, controllers/, logs/, etc.
    Public .htaccess blocks .env, .sql, .log, .md, .ini, .yml files

11. TOKEN RATE LIMITING
    Max 5 verification attempts per 15-minute window
    Prevents brute-force attacks on 6-digit tokens

12. AUDIT LOGGING
    Every admin action is logged with:
      - Who did it (admin_id)
      - What they did (action)
      - Details (details)
      - When (created_at)

13. NO eval() OR UNSAFE JS
    No eval() function used anywhere
    No inline event handlers for untrusted data
    Prevents JavaScript injection attacks

20. COMMON PROBLEMS AND SOLUTIONS
================================================================================

"Database connection failed"
  CAUSE: MySQL is not running, or wrong credentials in config/database.php
  FIX: Start MySQL in XAMPP. Check host/user/password in config/database.php.

"Invalid login" for all accounts
  CAUSE: The database has placeholder password hashes, not real bcrypt hashes
  FIX: Open http://localhost/SMEIC/public/generate_hashes.php in your browser

Page keeps redirecting to change-password
  CAUSE: force_password_change = 1 in your session
  FIX: Log in once with the default password. You'll be sent to change-password.
       Set a new password there. Or visit clear_force_change.php.

"500 Internal Server Error"
  CAUSE: A PHP error occurred
  FIX: Check logs/php_error.log for the detailed error message

Image upload fails
  CAUSE: The uploads directory is not writable
  FIX: Right-click public/assets/uploads/menu → Properties → Security →
       Edit → Allow Modify for Everyone (on XAMPP)

PDF export downloads as HTML
  CAUSE: dompdf library is not installed
  FIX: Run "composer install" in the project directory

QR code shows broken image
  CAUSE: chillerlan/php-qrcode library is not installed AND you're offline
  FIX: Run "composer install" OR connect to internet (uses online QR fallback)

Sidebar doesn't collapse on mobile
  CAUSE: Old browser that doesn't support modern CSS
  FIX: Use Chrome, Firefox, or Edge (latest version)

"Permission denied" error
  CAUSE: Trying to access a folder that's blocked by .htaccess
  FIX: This is CORRECT behavior. Only public/ should be web-accessible.

21. WHAT THIS SYSTEM IS NOT DESIGNED FOR
================================================================================

This is important to understand the limitations:

  ✗ Not designed for high-frequency trading or real-time collaboration
  ✗ Not designed for concurrent writes to the same wallet by the same user
    (the FOR UPDATE lock works per-request, not across requests)
  ✗ Not designed for audit-grade financial reporting
    (no double-entry bookkeeping, no immutable ledger)
  ✗ Not designed for HIPAA/PCI-DSS compliance
    (no encryption at rest, no audit chain-of-custody)
  ✗ Not designed for multi-currency or multi-region deployment
  ✗ Not designed for image processing or AI features

22. CAPACITY AND SCALABILITY
================================================================================

  Concurrent users:    50-150 simultaneous sessions
  Daily active users:  1,000-5,000
  Database size:       ~50 MB for 1 year at 500 students
  Order throughput:    ~100 orders/min sustained

KNOWN BOTTLENECKS (in order of impact):
  1. PHP file sessions — one file per user, locked during writes
